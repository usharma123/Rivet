# ADR 0005: Registry-signed audit trust policy

Status: accepted (revised)

Only the registry produces audits. Clients may request a new audit but cannot submit verdicts, evidence, or signatures. The registry signs each audit record with its Ed25519 key and verifies the signature before storage.

Every release is audited before it becomes installable. New releases start `pending`. Static analysis runs for every audit and checks install scripts, native binaries, obfuscation, embedded blobs, and file capabilities. The registry verifies npm provenance against the tarball digest, compares registry metadata with the tarball manifest, and scores changes from the previous release. Static findings remain authoritative even when dynamic probes run.

With `RIVET_AUDIT_MODE=gvisor`, the registry creates a fresh Docker volume for one gVisor trace session. A separate observer container receives kernel trace events through that volume. The audited workload receives only the canonical package tree, normalized manifest, and a supervisor-only evidence directory. Its package probes run as reserved UID 2000 with no effective, permitted, inheritable, or ambient capabilities; the supervisor retains `CHOWN`, `SETUID`, `SETGID`, `DAC_OVERRIDE`, and `KILL` for setup and process cleanup. The runner rejects a registry process using UID 2000, and the supervisor checks the evidence bind's actual ownership and mode before running probes. The workload has no external network access. The observer runs under `runc` and the package cannot mount its trace volume.

The registry gives each run a fresh nonce and checks the observer's workload container ID, start event, package execution, root supervisor completion marker, event limits, and final result. Before releasing the workload, it requires `runsc ps -format=json` to report only supervisor PID 1, then queries host `runsc trace list` for the exact container and requires the `Default` remote session with zero dropped events. This cumulative drop count covers all package activity through the supervisor marker; the sandbox control socket disappears after workload exit. It signs a gVisor result only after the workload and observer exit successfully. The signed evidence binds the artifact hash, canonical tree digest, and normalized manifest hash to the current request. Package-written hook reports remain advisory; only observer-owned network and honey-path events can raise the risk score. Dynamic observations cannot erase static risk.

The trace refuses trusted certification when package activity continues after the supervisor marker, when trace events are missing or dropped, or when the observer sees filesystem alias and namespace-changing syscall attempts that could hide reads. It also refuses successful `io_uring_setup`, any `io_uring_enter` or `io_uring_register` attempt, and supported `openat2` or new mount API attempts. The tested runsc release returns `ENOSYS` for `openat2`; gVisor emits no raw trace point for that failed syscall. Its `io_uring_setup` exit point omits task context, so the observer pairs it with the contextual enter point and refuses any successful setup in the sandbox. These checks were exercised with native ELF probes, including symlink and procfs alias reads through `mmap`, direct UDP send, and an `openat2` fallback. A `//tmp` honey path is normalized using Linux path rules before classification.

The supervisor probes each declared install script, main/module entry, and executable. Every declared target must have a successful applicable probe, and any timeout fails the run. The probes run without external network access and may lack package dependencies; a trusted observation means the bounded probes ran with a complete trace, not that every package behavior was exercised or that the package is benign. File reads through other untraced mechanisms and behavior outside these probes remain possible. A failure leaves the release without a certified gVisor audit.

Node is PID 1 in the workload and cannot reap an orphaned grandchild through its JavaScript API. If a package leaves a detached child or adopted zombie, `runsc ps` reports an extra PID and the registry refuses certification. Background-child packages may therefore remain unaudited until the supervisor has a native reaper.

The server uses `RIVET_AUDIT_AGENT_IMAGE` and `RIVET_AUDIT_OBSERVER_IMAGE` for the two images. `RIVET_AUDIT_RUNSC_BIN` points to a host-side command permitted to run only `--version`, `ps -format=json`, and `trace list`; `RIVET_AUDIT_RUNSC_ROOT` defaults to `/var/run/docker/runtime-runc/moby`. The runner requires the tested `runsc version release-20260601.0` before creating audit resources. The Docker daemon must register that same `runsc` binary and allow the per-workload `dev.gvisor.flag.pod-init-config` annotation. The command must be able to read that daemon's sandbox control state. A non-root registry deployment needs an administrator-provisioned, narrowly scoped helper for this trace query; a plain unprivileged runsc command fails closed. Rivet does not change the Docker daemon or grant this access itself. The disposable test helper and its source-backed DinD check are in `tools/e2e/runsc-gate.go` and `tools/e2e/audit-trace.sh`; the setuid helper is for that isolated test environment, not a production deployment. Build both images with `make audit-agent-image audit-observer-image` and check parser tests with `make audit-agent-check`.

Verdicts map to release states: low `active`, medium `warned`, high `quarantined`, critical `blocked`. Re-audits never undo `revoked`, `yanked`, or `archived`. `quarantined`, `blocked`, and `revoked` require explicit unsafe overrides at install and run time. Local BYOK evaluations remain advisory.
